# Repository State Agent Design

## Context

GStack Harness depends on Git state throughout the code workflow. GitNexus, bridge baseline, postchange reports, staged-scope review, and release gates all require a valid repository model: repo root, branch, HEAD, diff, staged files, and remote state.

The TPW-amz rehearsal exposed the current gap. A target project without `.git/` can still run parts of `pggg`, but later prerequisites fail independently: `baseline`, `postchange`, GitNexus refresh, and impact analysis cannot establish trustworthy facts. This makes Git a shared state layer, not an incidental tool.

## Decision

Add a required core **Repository State Agent**.

The user-facing shorthand can be **Git Steward**, but the system role should be named `Repository State Agent` because it owns repository facts, not just Git commands.

Repository State Agent becomes the single source of truth for:

- whether the target is inside a Git repository;
- whether the target root and Git root match or are intentionally different;
- whether HEAD exists;
- current branch or detached state;
- dirty, staged, and untracked files;
- session baseline;
- preexisting dirty files vs session changes;
- remote availability for release workflows.

## Placement

The agent sits after foundation installation/remediation and before Code Context:

```text
pggg / harness init
-> Foundation Readiness
-> Foundation Remediation if needed
-> Repository State Agent
-> Code Context Agent / GitNexus
-> Build / Review / Release
```

Foundation Readiness should still do a light Git probe, but should not own Git lifecycle. If repository state is missing or ambiguous, Orchestrator routes to Repository State Agent.

## Responsibilities

Repository State Agent owns:

- detecting `.git`, parent repo, repo root, branch, HEAD, remote, status;
- warning when target directory is not the Git root;
- detecting no-initial-commit state;
- creating or refreshing a session baseline artifact;
- separating preexisting dirty files from current-session changed files;
- checking staged scope before commit/review;
- validating remote readiness before release/ship;
- producing repository state artifacts and gate evidence.

It does not own:

- GitNexus semantic code analysis;
- code review findings;
- business code edits;
- release approval;
- destructive Git operations such as reset, rebase, force-push, branch deletion, or stash without explicit user approval.

## Interfaces

Repository State Agent writes:

```text
docs/REPOSITORY_STATE_REPORT.md
.gstack/repository-state.json
.gstack/git-baseline.json
docs/agents/repository-state.json
```

`.gstack/project-state.json` gains:

```json
{
  "repository_state": {
    "status": "ready",
    "mode": "target_project",
    "repo_root": "/path/to/repo",
    "target_dir": "/path/to/repo",
    "target_inside_repo": true,
    "branch": "main",
    "head": "abc123",
    "has_initial_commit": true,
    "dirty": false,
    "preexisting_dirty_files": [],
    "session_changed_files": [],
    "staged_files": [],
    "untracked_files": [],
    "baseline_status": "ready",
    "baseline_path": ".gstack/git-baseline.json",
    "remote_status": "missing",
    "warnings": [],
    "blockers": []
  }
}
```

Code Context Agent must read repository state before GitNexus refresh, baseline, impact, or postchange. Review Agent must read repository state before accepting a staged diff. Release Agent must require remote readiness or an explicit skip reason.

## Gate Model

Use three separate gates:

```text
Repository State: required for code-bearing target projects.
Repository Baseline: required for postchange, review, commit, and impact-sensitive work.
Repository Remote: required for release, ship, land, and deploy workflows.
```

`template_source` mode may continue with a repository warning for docs/protocol work. `target_project` mode should treat missing Git as partial for low-risk onboarding and blocked for review/release/postchange.

## Default Policy

```yaml
repository_policy:
  auto_init_empty_repo: true
  auto_init_existing_files: ask
  auto_initial_commit: ask
  require_git_for_code_context: true
  require_baseline_for_review: true
  require_remote_for_release: true
  protect_secrets_before_initial_commit: true
```

Safe automation:

- detect Git state;
- write repository reports;
- initialize Git for an empty target generated by the harness;
- recommend `.gitignore` entries for harness runtime artifacts.

Ask first:

- `git init` in an existing business directory;
- first commit;
- adding all untracked files;
- modifying `.gitignore` when it already exists;
- remote setup;
- stash, reset, rebase, force-push, branch delete.

## Problem Handling

Repository issues should route through Repository State Agent before generic Problem Handling:

```text
not_git_repo
no_initial_commit
git_repo_root_mismatch
git_status_failed
baseline_failed_not_git_repo
postchange_failed_not_git_repo
dirty_worktree_too_large
staged_scope_mismatch
remote_missing_for_release
```

Problem Handling records the outcome, but Repository State Agent decides whether the issue is warning, partial, blocked, or remediable.

## Minimum Viable Scope

The first implementation should:

1. add Repository State Agent to required core agent docs and generated team files;
2. add repository state fields to readiness/project state;
3. add a repository state report writer;
4. make Code Context commands fail early with repository-state evidence when Git prerequisites are missing;
5. add self-tests for no `.git`, no HEAD, ready repo, and remote missing for release.

Do not implement remote setup, stash, branch management, or automatic initial commits in the first version.
